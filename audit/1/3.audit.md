## 4. 重复失败根因分类

### A. ownership 边界没有被全局执行

`20260731-1106...owner-api-controller-architecture-review.md` 已经在连续外部 controller 失败后明确指出：runtime 与 negative-fixture AST domain 混合、external controller 同时拥有过多合同、repo owner 停在 composition boundary 以下，并要求 repo conformance owner。这个 reassessment 是正确的，也随后产生了 preparation、runtime、domain-template、parser 等 owner。

### B. representation contract 在不同 controller 中重复漂移

已重复超过三次的边界包括：raw bytes 与 decoded text、tuple/list、`MappingProxyType`/plain dict、machine-row marker/backtick、owner result wrapper、strict JSON 与 canonical JSON。当前尾部五个 fresh package 连续在 owner 前失败于：

1. accepted parser 收到 decoded text 而不是 exact bytes；
2. fresh source/root 与 PLAN/FULL read 的 effect order 颠倒；
3. exact-bytes/source type 或 mode 组合错误；
4. controller 不支持 accepted `ParsedMachineContract` wrapper；
5. deep-frozen `mappingproxy` 被直接交给 `json.dumps`。

第五次虽在内存中发现首个缺字段 `baseline.human_governance_override`，但 artifact write 为 0，未形成 sealed spec credit。当前 draft 只修 projection，不能补出该权威事实。

### C. wrapper/controller 自身错误多于 owner 错误

历史错误包含 marker、regex/AST domain、backtick、NUL/base64、shell/Python/JavaScript quoting、syntax、bytes/text、mappingproxy、EOF/global offset、apply_patch budget、Git metadata/stdout/budget、effect order、path/source type/mode、artifact positional binding 与转录错误。大量失败发生在 owner call 之前，不是 production owner 对 retained artifact 给出的业务判断。

### D. provenance 与 lifecycle 过度细分

Git argv/stdout/hash、terminal seal、ER physical EOF、supersession、read budget、retry=0 等局部 fail-closed 规则多数是合理的；问题是每个局部违约都被转换为新 task ID，而不是触发同一语义边界的 owner 重评估。S1/R1/D1/D2 往往只封存上一轮 handoff 或 attribution，并未改变 retained 状态。

### E. Orchestrator 状态机不一致

Planner 的局部 reject/accept 大多如实，但 Orchestrator 没有维护单一可信 active state：PLAN header、FULL top machine state、FULL 底部 handoff、ER physical EOF 与 HEAD 分别讲述不同阶段。fail-closed 防止了假 eligibility，却没有防止“同状态换 ID”的假推进。
