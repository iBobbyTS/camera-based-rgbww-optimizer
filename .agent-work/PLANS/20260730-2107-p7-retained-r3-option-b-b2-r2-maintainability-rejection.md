## Reviewed scope and proposed method

The reviewed package proposed one fresh pure-offline real-input B2 run. It would
read the four accepted C1 path-owner artifacts and three retained-R3 artifacts,
recompute the accepted five-entry Git provenance, and persist one subordinate
manifest plus terminal evidence. The committed preparation owner would admit the
terminal/ER linkage and the exact-five controller would retain phase ordering.

However, all filesystem and local-Git callbacks were assigned to a short external
Python source that the Executer would author only after activation. That source
would own seven non-following reads, identity/hash enforcement, read-only Git
object recomputation, canonical JSON persistence, partial-write/fsync/reload,
manifest/terminal seals and ER ordering without a dedicated repository test seam.

## Findings and decision rationale

The proposed launcher was not merely thin callback wiring. It formed a second,
high-risk I/O state owner whose source bytes and failure semantics could not be
tested before activation. This conflicts with the repository's maintainability
guardrails for persistence and error handling and would make B2/B3/B4 evidence
dependent on a one-off controller implementation.

Planner accepts the Orchestrator-owned engineering correction: first establish a
generic, repo-owned, dependency-injected provenance I/O boundary in exactly one
helper and one dedicated test. The helper must not absorb exact-five phase
ordering, retained schema/scientific facts, validator/eligibility, release or
device ownership.
