## 5. R1-003：Produced CR3 与 Failure Evidence

重构现有 runner 的 post-capture owner，按以下顺序处理：

1. 验证 capture result 的 `physical_capture_count` 是非 bool integer 且 exact `1`；
2. 解析 CR3 path，要求绝对解析后位于 current run、文件存在、regular、非空；
3. 禁止复用已由本 run 其他 capture ID 拥有的路径；
4. 完成第 2 步后立即把 actual produced CR3 计入 run physical ledger并原子持久化；
5. 随后验证 sidecar owner/path/hash、timing、quality、covariate和chronology；
6. 第 5 步失败时保留已产生 physical count，不得回滚，并在 `failure.json.rejected_capture` 保存
   capture ID、stage、CR3 path/hash、sidecar path/hash或缺失状态、timing evidence和current count；
7. 第 2 步失败时不得增加 physical count，failure 必须归类为 adapter/retained-CR3 evidence failure，
   不能声称已产生 CR3。

若 CR3 已有效但 sidecar 缺失/损坏，physical count 仍为 1，因为相机文件已经存在；该 capture 不得
进入 accepted formal ledger。若 result 报 2，但只提供 1 个有效 CR3，按实际 owned file 计 1 后
fail closed，并记录 reported count mismatch。

成功路径仍要求 plan 中每个 capture 恰好一个唯一、非空 CR3；不改变 existing physical caps。
